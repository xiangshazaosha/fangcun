# 方寸生产流程

本文件规定从一个题目到可交付演页的工作顺序。实现代码统一引用 [code-reference.md](code-reference.md) 的编号。

## 1. 素材与需求入口

按 [intake.md](intake.md) 的五项入口收集缺失信息，开工累计最多五题；用途与篇幅从内容推断，动态模型不单独加题。用户不选时使用其中的默认值继续制作，不反复确认。不要在开工前询问部署包或 PDF。不要让用户解释抽象设计术语，只让其选择“海洋风、透明玻璃风格、双色风或看三种样式”；先看内容和素材，再落地视觉方向。[代码 C04、C05、C07、C14]

收到素材后建立清单：

| 类别 | 要检查什么 | 处理方式 |
|---|---|---|
| Logo | 透明背景、横竖版、可读区域 | 用户未提供专用 Logo 时使用“方寸 / FANGCUN”默认资产；不得使用 CSSC [代码 C05] |
| 动态模型 | 格式、透明度、时长、是否可循环 | 自动播放或指针拖动；始终准备后备图 [代码 C07] |
| 背景 | 默认动态海浪 / 用户视频 / 无动态背景 | 未选择时默认无动态背景；视频叠加遮罩并准备 poster [代码 C04、C14] |
| 图片/截图 | 分辨率、文字可读性、是否有敏感信息 | 围绕图片设计页面，不把图片硬塞进已满页面 [代码 C06] |
| 文案/资料 | 哪些是事实、哪些是建议、哪些不能改 | 形成事实底稿，不补造业务含义 |

## 2. 建立三层内容文档

复杂项目先写三层内容，不直接开写 HTML：

1. `content-source.md`：原始资料与事实底稿。
2. `slide-copy.md`：逐页可见文字；每页标明标题、正文、结论。
3. `storyboard.md`：每页的讲解目的、版式、素材、动效和交互。

简单项目可合并为一个 `storyboard.md`，但必须能区分事实与设计表达。

故事板中每页至少写：

```text
页码 / 标题
这页要让观众明白什么
页面上真正出现的文字
主要视觉
是否逐项呈现
是否交互；如果交互，输入、状态、反馈、结论、重置分别是什么
使用的本地素材
```

## 3. 确定密度和叙事节奏

- 现场讲：一页一个重点，正文尽量少；用章节页、演示页和结论页拉开节奏。
- 自己看：页面可更完整，但通过分组、图表和注释维持层级。
- 章节通常采用“提出问题 → 建立模型 → 展示过程 → 给出结论/行动”。
- 只有当用户操作能帮助理解变化或因果时才做交互。[代码 C10—C13]

## 4. 建立可替换的视觉系统

先从 [style-catalog.md](style-catalog.md) 选择风格，再根据 Logo、主体素材和场景决定可替换的颜色与字体。将主题值写成 CSS 变量，不在组件里散落硬编码色值。[代码 C14、C23]

至少定义：背景色、正文色、弱文字色、主强调色、辅助强调色、玻璃材质、圆角、字体和动效缓动。

用户没有提供本次专用品牌时，使用“方寸 / FANGCUN”默认 Logo，并保持所选风格自身的色彩纪律；Logo 身份色不能扩散到整个主题。只有用户明确选旧海浪视频或实时海洋场景时，才载入对应素材；两者不能混淆。[代码 C04、C05、C14、C23]

## 5. 先做三类样页

先检查背景与粒子开场是否已主动询问（或用户已明确给值），不能用暂时关闭替代问过。整套故事板必须标出内容适配的游戏位置及规则；短样稿至少验证一个真实玩法，长稿分布多个不同机制。启动器生成的是演示骨架，不是自动完成了用户的互动游戏。

正式铺满整套之前，先完成并截图检查：

1. 封面或章节页：检验 Logo、标题、背景和动态模型。[代码 C04、C05、C07]
2. 普通高密度内容页：检验文字、卡片和层级。[代码 C14]
3. 最复杂互动游戏页：检验选择后果、规则、成功/失败反馈、重玩、状态隔离和可用性。[代码 C09—C13、C41]

样页通过后再扩展整套，避免做完才发现视觉系统或交互架构不成立。

## 6. 推荐文件结构

新选题默认放入独立目录，避免覆盖现有示例：

```text
decks/<topic-slug>/
├─ build_deck.py          # 可选；复杂演示建议使用，作为唯一源文件
├─ index.html             # 浏览器入口
├─ README.md              # 启动、导航、资源说明
├─ start-ppt.bat          # 需要内网/离线交付时提供
├─ content-source.md
├─ slide-copy.md
├─ storyboard.md
└─ assets/
   ├─ logo/
   ├─ media/
   ├─ images/
   ├─ icons/
   └─ fonts/
```

简单演示可以只维护 `index.html`；一旦使用生成脚本，脚本就是唯一源文件。[代码 C17]

## 7. 实现顺序

1. 固定舞台和页面状态。[代码 C01、C02]
2. 主题变量与通用组件。[代码 C14]
3. 背景、Logo、模型和媒体后备。[代码 C04—C07]
4. 翻页与逐项呈现。[代码 C03、C08]
5. 按故事板加入少量关键交互。[代码 C09—C13]
6. 减弱动效与无障碍。[代码 C16]
7. 可编辑封面信息与页码深链（确有需要时）。[代码 C19、C21]
8. 打印、导出和本地启动能力。[代码 C15、C18、C22]

## 8. 浏览器验收与部署包

交付前按照 [qa-checklist.md](qa-checklist.md) 检查。检查通过后启动本地 HTTP 服务，直接在浏览器打开给客户验收。此时只交付可验收的浏览器版本，不预先制作部署包。

成品完成后最后询问客户是否需要部署包。客户确认需要时再生成 ZIP；包内至少包含 `index.html`、全部资源、适用平台的启动脚本和 `README.md`。说明文件写清启动步骤、访问地址、浏览与交互方式、重置/退出方法、目录结构和常见问题；离线或内网包必须在全新解压目录中断网复测。[代码 C06、C15、C18]

## 9. 成品冻结和风格回收

完成后按 C36 保存到 `成品/<演示名称>/`。用户要求抽为新风格时，执行 [style-extraction.md](style-extraction.md)；先冻源，再分出风格、通用机制、可选素材、专有文案，最后在全新目录完成运行与截图检查。新分类只追加，不覆盖既有双色风/透明玻璃风。[代码 C34–C36]
